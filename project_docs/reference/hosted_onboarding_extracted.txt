Overview
Hosted Deployment is a managed deployment service that allows users to quickly deploy AI agents, MCP servers, or general web services with built-in elastic scaling andflexibility. It abstracts infrastructure management, enabling teams to focus on agent design and business outcomes rather than operational details. It is provided as a part ofOCI Generative AI service, and you may click OCI Generative AI to learn more.
This document introduces the Hosted Deployment service and explains how to get started. It provides two step-by-step tutorials to help you onboard: one for deploying anMCP server and another for deploying an AI agent.

Introduction
The Hosted Deployment service provides two major resources: Application and Deployment. An Application defines the configuration for how your container image shouldbe deployed, such as networking, scaling, and authentication settings. A Deployment is created within an Application and references a specific container image in OracleCloud Infrastructure Registry (OCIR). Creating a Deployment provisions the underlying infrastructure and starts the application, making it running and accessible.
At this time, OCIR is the only supported image registry. Click here to learn more about  Oracle Cloud Infrastructure Registry .
Deployment Scaling Configuration
Hosted Deployment supports autoscaling, which controls how many copies (replicas) of your application run at any given time.
You can configure:
Minimum replicas – the lowest number of running copiesMaximum replicas – the highest number of copies allowed during scalingAutoscaling metric – choose one of CPU, Memory, Concurrency, or RPSThreshold – set the target threshold for the selected metric to control when the application scales up or down
You may set the minimum replicas to 0. When there is no incoming traffic, the application scales down to zero replicas to reduce costs.
Environment Configuration
Hosted Deployment provides managed storage services and environment variables that your application can use at runtime.
Managed Storage
Managed storage supports OCI Database with PostgreSQL, OCI Cache (Redis), and Oracle Autonomous Database (ADB). For each storage type, you can specify anenvironment variable name so the connection URI is injected into your application at runtime. Click here to learn more about OCI Database with PostgreSQL, here to learnmore about OCI Cache, and here to learn more about Oracle Autonomous AI Database.
When configuring storage for an application, you can either create a new storage resource or choose an existing one. Reusing existing storage lets multiple applications sharethe same backend instance, for example a shared ADB instance.
Environment Variables
You can also define custom environment variables to control application behavior at runtime. Environment variables are commonly used to configure values such as API keys,feature flags, or environment-specific settings.
Networking Configuration
Networking determines how your application connects to other networks and how users access your application.
Networking Type (Outbound Traffic)
This setting controls outbound network access from your application.
Default. Allows access to OCI services and the public internet.Custom. Enables private access to a specified VCN and subnet. Click here to learn more about OCI Networking.
Endpoint Type (Inbound Traffic)
This setting controls how users access your application.
Public. Exposes the application to the public internet.
Authentication Configuration
Authentication controls who can access your application.
Identity Domain. Enables federated authentication using OCI Identity Domains or an external identity provider. Click here to learn more about OCI Identity Domain.
Deployment Configuration
Multiple artifacts can be associated with a Hosted Application, but only one artifact can be active at a time.The application endpoint remains unchanged throughout the lifecycle of the application, regardless of which artifact is active.When switching the active artifact, the service performs the transition using a blue-green deployment strategy to ensure a smooth and uninterrupted rollout.
Container Requirement and Restrictions
Your Docker container running in the Hosted Deployment environment must meet the following requirements. 
Host and Port
1. The container must listen on host 0.0.0.0.2. The container must listen on port 8080.
Http Response Content Type
The container must expose an HTTP-based service that implements REST-style request/response endpoints with methods of GET, PUT, POST, DELETE, PATCH usingcustomer defined paths.
The platform determines whether a request expects a streaming response by inspecting the Accept header.
If the Accept header contains text/event-stream, the endpoint returns a Server-Sent Events (SSE) response with content type: Content-Type: text/event-stream

Otherwise, the endpoint returns a standard JSON response with content type: Content-Type: application/json 
This mechanism allows a single endpoint to support both streaming and non-streaming interactions in a consistent and backward-compatible manner.
Readiness Endpoint
The docker container must expose the readiness endpoint to verify that the application container is fully initialized and capable of handling incoming requests.
Path: /readyPurpose: Indicates whether the container is ready to receive trafficResponse Format: HTTP status code onlyContent-Type: application/jsonSuccess Status Code: 200 OK (application is ready)
If the container is not ready, the endpoint should return a non-200 status code to prevent traffic routing.
Liveness Endtpoint
The docker container must expose the liveness endpoint to verify that the application container is not in a stuck or unrecoverable state and does not require a restart.
Path: /healthPurpose: Detects whether the container is alive and functioningResponse Format: HTTP status code onlyContent-Type: application/jsonSuccess Status Code: 200 OK (application is healthy)
If the application enters a deadlock or unrecoverable state, this endpoint should return a non-200 status code, allowing the orchestration platform to restart the containerautomatically.
Reserved Environment Variables
The following environment variables are reserved for system use. Please avoid declaring them in your container code. 
Image Architecture
The image must be buit with linux/amd64 platform as example shown below.
File Access
The container local file system is readonly, only path /tmp is writable in the file system. Therefore if the code need to write files to local file system, please write to /tmp.
Vulnerability Scanning
Before deployment, the image will be scanned via OCI Vulnerability Scanning Service and fail if there is any Critical findings for security concern. Note: We recommend youto use base images provided by OCI container registry https://container-registry.oracle.com/ all images of where passed vulnerability scanning.
Other restrictions
The customzed entry point command is not supported at the moment. So please integrate the entry command into Dockerfile using CMD or ENTRYPOINTThe volume mapping is not supported at the moment which means local file persistence is not supported. Please make your service stateless otherwise the local fileswill be gone during redeployment or node replacement.
